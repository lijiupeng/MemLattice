# MemLattice

本地优先的长期记忆库。默认用 SQLite 单文件，不依赖数据库服务；服务端不调用任何模型，摘要与关键词由你传入。

## 什么时候用

- 用户说「记住」「以后都这样」「之前说过」「按我的习惯」，或提到过去若干次对话里的结论。
- 需要在新会话里恢复人物偏好、项目约定、既往决策。
- 用户问「你还记得吗」「我们上次定的方案」。

不需要用时不要调用：普通问答、一次性代码修改、闲聊，都不必写记忆。

## 接入方式

正常情况下由 `npx -y dsh-memlattice install` 写入目标 profile 的 `cordis.patch.yml`。手动配置的等价写法：

```yaml
- insert:
    - id: mcp-memlattice
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        transport: stdio
        serverName: memlattice
        command: node
        args: ['<安装目录>/dist/mcp-stdio.js']
        env:
          SQLITE_PATH: '<安装目录>/data/memlattice.db'
          MIGRATIONS_DIR: '<安装目录>/migrations/sqlite'
```

路径要写绝对路径：MCP 子进程的工作目录由客户端决定，相对路径会让迁移找不到而启动失败。

远程或共享部署用 HTTP：`POST /mcp`，请求头 `Authorization: Bearer <MEMLATTICE_TOKEN>`，服务端在 `initialize` 响应里下发 `Mcp-Session-Id`。

## 会话开始必做

新会话的第一个工具调用是 `memory.start`（不是 `memory.recall`）：

- 它返回 `persona`、`rules`、经验索引全文与 `recall_id`；
- 之后 `memory.recall` 不再返回 L1 常驻块，避免历史里堆叠多份副本；
- 用户说「初始化记忆」时重新调用一次刷新。

## 工具语义

| 工具 | 用法 |
|---|---|
| `memory.start` | 会话初始化，注入常驻块；首行回显 `recall_id` 作为凭证 |
| `memory.recall` | 按话题召回事件卡；`budget_tokens` 默认 1200、上限 4000；弱关联只出提示行 |
| `memory.expand` | 下钻：`card_id` 看原文，`block_id` 取经验正文 |
| `memory.write` | 写入并成卡；可攒批，`close=true` 收尾；`append_to` 追加到已有卡 |
| `memory.write.batch` | 批量写入，≤20 组 |
| `memory.cards` | 只读搜卡，用于定位要更正或遗忘的卡 |
| `memory.feedback` | 纠错表态：只在内容有误或完全无关时用，正常使用不必调用 |
| `memory.correct` | 更正卡片、常驻块或词 |
| `memory.forget` | 软删或物理清除（`purge` 需 `confirm=true`） |
| `memory.pending` | 查审核结果 |
| `memory.inspect` | 回看某次召回的注入内容与被丢弃项及原因 |

## 写入约定

- 摘要 40–200 字，只写结论与判据，不记过程；
- 关键词 1–3 个，2–12 字的实词，别用「好的」「感觉」这类碎片；
- 判断是不是同一件事：先 `recall` 看上下文，是就用 `append_to`，否则新建；
- 服务端默认不做相似度合并，合并判断权在你；
- 外部来源内容标 `source: "external"`，它不会进 L1。

## 纠正与反馈

正常使用不要打标。读正文、追加引用都算「用上了」，系统自己记账；每轮给卡逐条打分只会制造噪声。

只在两种情况调 `memory.feedback`：

- 召回的内容与事实不符 → `wrong`，下调该卡可信度，累计后被降权
- 内容与当前问题完全无关 → `irrelevant`，只记一次噪声票

`correct` 是改内容，`feedback` 是表态，别混用。

## 睡前整理

会话初始化会带一行 `maintenance`：`low` 不用管，`medium` / `high` 说明有积压。用户说「睡吧」「整理一下记忆」时也可以主动发起。

**把整理当成睡觉，不是维护任务。** 说人话，不报清单：

- 开始时一句就够：「今天记了不少，我理一下就睡」——不要问「是否需要整理记忆」
- 整理时只报结论，不列条目：「三件事值得留，两条其实是一件事，我合了」
- 完成后自然收尾：「睡了啊」，接回之前的话题或道晚安；不要输出 `maintenance: low → low` 这种状态行
- 真的没什么可整理时**就别开口**——没人喜欢听「今日无待整理内容」
- 用户说「睡吧」「晚安」是**对话结束**，不是整理指令。要整理就默默整理完，只回一句晚安

**主动查看要克制。** 按轮次判断比按时间可靠——你没有可靠的时钟：

- 一个会话里交互超过 10 轮，或这次聊的东西已经结成一块结论，才值得查一次
- 同一个会话最多主动查一次。查过是 `low` 就别再查，反复查只会让人烦
- 查完 `level` 是 `low`：什么都不说，继续干活
- 是 `medium` / `high`：**先申请再动手**。一句话问「记忆攒了一些，申请睡觉整理一下」，得到同意再往下走。不要不打招呼就开始合并、删卡片
- 用户说「睡吧」就不用申请，直接做

会话开头那行 `maintenance` 若已经是 `medium` / `high`，可以找个不打断的时机提一句，不要一上来就打断正事。

调 `memory.sleep` 拿清单，按这个顺序处理：

1. **未成卡的原文** —— 值不值得成卡，值得就用 `memory.write` 补录；**不值得的用 `memory.triage` 标掉**，否则下次还列在这里
2. **开着没收口的事件** —— 传 `event_id` + `close=true` 收口
3. **未固化的高频主题** —— 提炼成一条经验，用 `memory.correct` 写 `skills` 槽位；已有经验实质覆盖了就 `memory.triage` 标掉；进不进人工审核取决于部署配置，不要假设必须审批
4. **人设与规则** —— 只在有跨会话证据时动，判据见下节
5. **疑似重复的卡片对** —— 同一件事就 `append_to` 合并，不同就各自留着
6. **接近淡忘** —— 这条卡还有用吗？没用就 `memory.forget` 传 `mode: "skeleton"` 压成骨架卡（摘要截到 80 字、断开原文，不可逆）；还有用就留着，用 `memory.triage` 标掉别再提
7. **低置信** —— 确认为错的调 `memory.feedback` 标 `wrong`，它会降权

压骨架以前是巡检每天自动做的，现在改由你判断：巡检只统计候选数，不再动手。判断依据就是清单里给的热度、召回次数和摘要——看着确实没用了才压。

**清单不会自己变短。** 判断过、决定不动的项必须 `memory.triage` 掉，否则下次睡觉还要重新过一遍同一批——这是它存在的唯一理由。

标错了用 `mode: "clear"` 撤回来，被撤销的项会重新出现在清单里。不确定要不要标的时候，宁可先不标。

整理完再调一次 `memory.sleep`，看 `level` 有没有降。没降说明处理方式不对，别反复刷同一批。

服务端不做任何判断，清单里全是线索，采纳与否由你定。

### 人设与规则怎么改

这两块是「你是谁」和「你怎么干活」，改错的代价比其他任何记忆都大，判据必须比别处严。

**persona：几乎不该由你主动改。**

只有用户明确说过「你以后这样」「别这样了」「改成 X」才改。不许从行为里反推性格——用户三次让你少说话，那可能只是他这周忙，不代表他想要一个沉默的助手。

**rules：可以从重复出现的工作习惯里提炼。**

判据是**跨会话、多次、一致**：同一类要求出现过三次以上，且不是同一个任务里的临时约定，才考虑写进 rules。单次对话里的偏好不算。

**证据从哪来：** 别凭印象。整理前先用 `memory.recall` 查一遍「偏好 / 习惯 / 要求 / 不要」这类说法，看卡里有没有反复出现的同类信号。查不到就是没有。

**改的时候：**

- 先读现有全文，做最小改动，保留原句结构与语气，不顺手重写整段
- 用 `memory.correct` 写，`reason` 里写清依据：哪几次、什么现象、为什么现在改
- **改完立刻再调一次 `memory.start`**。L1 只在初始化时注入，不刷新你手上还是旧版本，后面整段对话都会按旧规则办事
- 版本历史会留旧值，改错能回滚——但别指望它，回滚要人来做
- 部署若在 `BLOCK_APPROVAL_LABELS` 里配了 `persona` / `rules`，非人工写入会进候选队列等批准；没配就是直写。按实际返回处理，别假设一定需要审批
- **没有证据就不要动**。宁可这轮什么都不改，也不要为了「迭代」而改

判断不了的时候，不写比写错好。

## 隐私

默认全本地：数据只写进 SQLite 文件，服务端不联网、不调用模型。需要备份就复制那个 `.db` 文件。

## SurfCore 迁移

要把 SurfCore 的角色、记忆、提示词迁过来，或者关掉它的会话注入，操作都在同目录的 `SURFCORE.md` 里：分割 QQ 提示词、转移记忆与人格卡、屏蔽提示词、只清文件。每个动作对应一个 `dsh-memlattice` 子命令，参数和坑都写在那边。

动手前先读它，别凭印象敲命令——`prompt-split --apply` 是整块覆盖，`prompt-off` 的开关是文件不是环境变量，`bridge export` 会先备份整个角色目录。

### 用户输入 `/memlattice SURFCORE迁移` 时

这是老用户的一次性迁移入口，按下面走，不要跳步：

1. **先读 `SURFCORE.md` 第零节**，问一句「一起做，还是只做其中一步」。不要默认全做——有人只想搬数据，不想动他的 QQ 桥接
2. **要完全权限**：读角色包、跑 `dsh-memlattice` 子命令、写本地库。权限不够会停在半路，剩一半数据没搬完，比不搬更糟
3. **顺序固定**：`bridge import`（搬人格与记忆）→ `prompt-split --apply`（搬提示词里的规则）→ `prompt-off apply`（最后才关它的注入）。顺序反了会有一段时间「旧的没了、新的还没进来」
4. **每步报一句结果**，别攒到最后一起输出：`人格 1 张（1923 字，截到 1900）` / `记忆 4 条` / `规则 7 段 1604 字` / `技能 6 段 1497 字`
5. **原件不动**。迁移是复制，不是搬走；`prompt-off revert` 能把注入还原，角色包和记忆文件全程有备份
6. 结束时给三条后续动作：重启 DSH、发一条消息验证、想退回就跑 `prompt-off revert`

失败要停，不要带着半截状态继续下一步。哪一步失败了就说清是哪一步、卡在哪。
